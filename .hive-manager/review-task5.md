# Task 5 Review

## BLOCKING
- M2.1 is not actually wired into later turns. `GeminiSessionViewModel.startSession()` resets `SessionStateManager` before connect, and `GeminiLiveService.sendSetupMessage()` is the only place that calls `buildSystemInstruction()` (`samples/CameraAccessAndroid/app/src/main/java/com/meta/wearable/dat/externalsampleapps/cameraaccess/gemini/GeminiSessionViewModel.kt:71`, `samples/CameraAccessAndroid/app/src/main/java/com/meta/wearable/dat/externalsampleapps/cameraaccess/gemini/GeminiLiveService.kt:84`, `220`, `262`). The entity/objective state is only populated later in `onTurnComplete()` / `observeText()` (`GeminiSessionViewModel.kt:94`, `samples/CameraAccessAndroid/app/src/main/java/com/meta/wearable/dat/externalsampleapps/cameraaccess/openclaw/ToolCallRouter.kt:114`), so Gemini never receives refreshed session context after turn 1. In the active session, "Send it to him" cannot rely on the new session-state data across 3+ turns because that data is never resent.
- M2.4 regressed out of HEAD. `GeminiUiState` no longer carries `pendingConfirmation` (`GeminiSessionViewModel.kt:23`), `GeminiOverlay()` renders only `ToolCallStatusView` and `SpeakingIndicator` (`samples/CameraAccessAndroid/app/src/main/java/com/meta/wearable/dat/externalsampleapps/cameraaccess/ui/GeminiOverlayView.kt:64`), `StreamScreen` passes no confirm/cancel callbacks (`samples/CameraAccessAndroid/app/src/main/java/com/meta/wearable/dat/externalsampleapps/cameraaccess/ui/StreamScreen.kt:134`), and `ToolCallRouter` exposes only a private `PendingConfirmationController` (`ToolCallRouter.kt:50`). The integrated `86fbd9e` UI work is missing in the current tree, so there is no pending-confirmation overlay between `ToolCallStatusView` and `SpeakingIndicator`, and no UI path sharing the `confirm_pending` flow.

## HIGH
- The context budget is still char-based, not deterministic token-based. `SessionStateManager` enforces `MAX_CONTEXT_CHARS = 800` and truncates by string length (`samples/CameraAccessAndroid/app/src/main/java/com/meta/wearable/dat/externalsampleapps/cameraaccess/operator/SessionStateManager.kt:55`, `226`), and the regression test only asserts `block.length <= 800` (`samples/CameraAccessAndroid/app/src/test/java/com/meta/wearable/dat/externalsampleapps/cameraaccess/operator/SessionStateManagerTest.kt:11`). The acceptance criterion called for a deterministic `<=200`-token context block; this implementation can overshoot or undershoot that budget depending on content.

## MEDIUM
- None.

## LOW
- There is no automated coverage for the pending-confirmation UI/lifecycle path. The current tests cover generic routing failure, tool declaration wiring, and `SessionStateManager` primitives (`samples/CameraAccessAndroid/app/src/test/java/com/meta/wearable/dat/externalsampleapps/cameraaccess/openclaw/RoutingAndToolResultTest.kt`, `samples/CameraAccessAndroid/app/src/test/java/com/meta/wearable/dat/externalsampleapps/cameraaccess/operator/SessionStateManagerTest.kt`), but nothing asserts overlay presence, confirm/cancel callbacks, timeout auto-hide, or reconnect-note timing. That left the M2.4 regression undetected.
